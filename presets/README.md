# 视觉小说 4K 显卡预设

三份 JSON 分别对应 RTX 5090、RTX 5080、RTX 5060 Ti，使用本项目移植的神经网络模型替换旧版视觉小说包的 CuNNy 超分链。目标为 SDR 游戏窗口放大到 3840×2160；末级按屏幕等比适配，不拉伸画面。

## 导入和选择

在 Magpie 的“缩放模式”页面导入对应 JSON，然后统一在“配置文件 → 默认 → 缩放模式”中选择，不建立作品专用配置。每份文件包含两档，括号里的分辨率指**游戏捕获尺寸**，不是显示器分辨率。

| 显卡与文件 | 720p／900p 原画 | 1080p 原画 |
| --- | --- | --- |
| [燃烧5090](gal-artcnn-5090.json) | ARNet-F8B8 2× → Anime4K Restore UL → ArtCNN-C4F16 2× → SSimDownscaler | ArtCNN-C4F32-FP32 2× → Lanczos |
| [燃烧5080](gal-artcnn-5080.json) | ArtCNN-C4F32 2× → C4F16 2× → SSimDownscaler | ArtCNN-C4F32 2× → Lanczos |
| [燃烧5060 Ti](gal-artcnn-5060ti.json) | ArtCNN-C4F16 2× → C4F16 2× → Lanczos | ArtCNN-C4F16 2× → Lanczos |

例如，1280×720 经过两遍模型得到 5120×2880，再缩到 3840×2160；1920×1080 经过一遍模型即为 3840×2160。《跨次元恋人！！》当前窗口捕获为 1280×720，应选择对应显卡的 720p／900p 档；《国王恋爱 Ver1.00》测试窗口捕获为 1920×1080，应选择 1080p 档。切换不同原画分辨率的游戏时，在“默认”中手动切换对应模式。

先让游戏以原生分辨率运行。若游戏先自行拉伸到 1080p，再套用 1080p 档，模型收到的已经是插值画面。低于 540p 的原画放大到 4K 时，不要直接使用包含 SSimDownscaler 的双重超分档：其四倍中间图仍可能小于目标，必须另行调整链路。

## 配置取舍

- **5090 在正常游玩的前提下优先画质，不以节电为目标。** 首选“4K精细重建（720p／900p）”：ARNet 先重建轮廓；在两倍尺寸上进行一次 Restore UL 线条修复；ArtCNN-C4F16 再次重建；最后用 SSimDownscaler 缩到屏幕，`oversharp=1.0`。
- 中间尺寸的修复比放在最后更适合当前 720p 游戏的轮廓与细笔画；第二遍 C4F16 在已修复输入上保持了良好的细节，不按模型规模决定 5090 档位。
- **5090 的 1080p 档使用“4K保真重建”。** 一遍 C4F32-FP32 直接重建到 4K。针对《国王恋爱》的文字、人物与背景，以及另两组配对壁纸的比较中，额外叠加 Restore、锐化或先放大到 8K 再缩小，没有带来稳定的额外细节收益，部分组合会加重线条，因此保留单遍模型。
- `ArtCNN-C4F32-FP32` 与原 C4F32 使用相同权重和 16 位中间纹理，只强制着色器算术使用 FP32。本机 RTX 5090 D 的 FXC／Shader Model 5 路径中，此变体显著快于原 `min16float` 路径；这不代表 FP32 普遍比 FP16 快，也不能据此推断其他显卡的表现。生成入口仍为 `scripts/generate_neural_effects.py`。
- 5090 两档已分别针对指定的 720p 和 1080p 游戏筛选；5080、5060 Ti 的条目仍为先前方案，尚无对应显卡上的实测结论。
- **5080 降低第二次重建的开销。** 第一遍仍用 C4F32；第二遍运行在四倍像素数的画面上，改用 C4F16 比只减轻第一遍更能节省运算。
- **5060 Ti 同时面向 8GB 和 16GB。** 使用 C4F16 和单阶段 Lanczos 收尾。按效果源码中的纹理尺寸估算，720p／900p → 4K 的效果纹理约为 524／801 MiB，1080p → 4K 约为 253 MiB。这不包括游戏、捕获缓冲、桌面、驱动及显存分配开销，也不是整机显存实测。
- 1080p 原画经过一遍 2× 模型即可到 4K，不为显卡档位强加第二遍模型。5090 使用独立的 FP32 算术变体，5080 保留原 C4F32 路径；更换显卡后应实测开销再选择。
- Lanczos 的 `ARStrength=0.75` 用于抑制文字和高反差边缘的振铃。5090 首选链只做一次中间线条修复，不再叠加 CAS、AdaptiveSharpen 或 Deband；这些处理在当前素材中没有提供足以抵偿细节改写的稳定收益。

这里只提供项目已有模型的组合，不下载模型，不要求 ONNX、CUDA 或 TensorRT 插件。ARNet、ArtCNN 和 Anime4K 使用项目现有的 HLSL 渲染路径；模型名称不意味着调用显卡 Tensor Core。保留 Magpie 的全局 FP16 支持即可，C4F32-FP32 会自行选择 FP32 算术。若导入时找不到该效果，需同时更新程序目录的 `effects/ArtCNN/ArtCNN-C4F32-FP32.hlsl`。

当前 ONNX 后端只显示与当前完整输入一致的模型结果；连续变化的画面可能长期停留于预览。用户明确排除 IllustrationJaNai DAT2，也不接受秒级出图作为日常游玩方案，因此 AnimeSharp 和 IllustrationJaNai 不加入这些游戏预设。更高的静态图片画质不能替代游戏中实际可用的连续输出。

## 运行与能效

5080、5060 Ti 可以在使用该模式的配置文件中启用 60 FPS 限制；30 FPS 游戏也可按游戏帧率设置。保持重复帧检测为动态或始终检测，避免对静止 CG 反复执行整条链。帧率限制属于应用配置文件，不包含在可导入的缩放模式 JSON 中。

若 5060 Ti 的低分辨率档仍然开销偏高，可以选择同一文件的单遍“1080p”档处理 720p 游戏：此时先模型放大到 1440p，再由 Lanczos 补到 4K，以部分细节换取更低开销。16GB 显存不代表可以按比例提高模型计算量。

模型来源：[ARNet／ACNetGLSL](https://github.com/TianZerL/ACNetGLSL)、[ArtCNN](https://github.com/Artoriuz/ArtCNN)、[Anime4K](https://github.com/bloc97/Anime4K)。当前首选是针对指定游戏素材作出的取舍，不承诺跨游戏的固定画质排名或帧率。
